# Non-square tactical MAP save roundtrip

## Scope

`tests/test_save_world.c` adds a separate private-slot roundtrip after the existing 257-item FLOBJS test. It starts from the real `World_NewGame` craft 0 and checks `Craft_CountSoldiersAboard(...,0)==8` before mission setup. It then constructs a normal Forest mission with the observed type-2, mode-0, layout-1, craft-0, tier-1, terrain-variant-2 tuple. `Game_SeedRngFixed` is called after `World_NewGame` so map placement uses the fixed test seed 3000 (30 warm-up draws) without changing the generated Soldiers' stats.

The fixture uses the original inventory screen and public confirm-key path. Its `TactInputHooks.pfnInvCloseAndCommit` test hook calls `World_InvCloseAndCommit`, the same public function the app hook calls. Before declaring 6x5 geometry, the test reads `plane.ma1` through `MapTemplate_Load` with flag 3 and checks the complete layout-1 plane footprint at the builder's craft tile. It also checks the staged deploy cell, parked Soldier cell references, and all existing unit/item owners outside the retained rows. It then declares `pMap->geom` as 6x5 before the normal confirm deploy. The parked crew may share the deploy cell without each owning it at this stage; after confirm, the full pre-save gate requires every Soldier cell to have one reciprocal owner. Mission actors come from `Tact_InitMission`; the fixture does not move/remove units, alter roster/counts/stats, or inject cell owners.

This is a test-only geometry case, not a claim that the original terrain builder makes a 6x5 map. The builder first creates the original 6x6 mission. The fixture keeps that mission's normal craft and deployment paths, bounds the live references to the retained region, and calls the real `World_SaveSlot` writer on 6x5 geometry. It does not patch a save header or change a record stream after writing. The natural-ground run log at `build/e2e_normal_ground/run_20261026T192954Z_865/normal_ground.log:261,283-327` recorded the same Forest/mode-0/layout-1 metadata and eight deployed XCOM cells at rows 39..42, all on z=1; the test uses preflight checks on its own fixed-seed placement rather than forcing those coordinates.

The prior XCOM-base/layer-0 fixture correctly failed its spatial gate: the executor diagnostic found Soldier pool index 6 owning `(51,52,0)`, which is outside the 6x5 region. That fixture was left unmodified; the replacement builds the normal layout-1 mission and deploys its existing crew through the real confirm path.

## Original wire contract

Evidence is the raw ARM instruction stream in `pufobeta.exe.i64`; the instruction words and operands below are from the read-only disassembly/byte reads.

- `Save_WriteMap @ 0x438E0` writes the X and Y dimension bytes before cell records. `0x438F8: E3A02001` sets the first write size to 1; `0x43908: EB016EE9` calls `DatFile_Write` with the pointer to `Map+0x1511B`. `0x43918: E3A02001` sets the second size to 1; `0x43920: EB016EE3` writes `Map+0x1511C`.
- The writer loads dimX at `0x4392C` and dimY at `0x43938`. `0x4393C: E3A0B000` starts the layer offset at zero; `0x43940: E3A0800A` sets 10 cells per map tile. `0x43948..0x4394C` form `10*dimY` rows and `0x4395C..0x43960` form `10*dimX` columns.
- `0x43970: E08B3009`, `0x43974: E3A020F0`, `0x43978: E0020293`, and `0x4397C: E0825006` form a row base with a 0xF0-byte pitch, or 60 four-byte cell pointers. `0x4398C` loads the pointer from the cell table at `Map+0x15338`; `0x43C2C: E2855004` advances one pointer per column. `0x43C54: E2899001` advances the row. `0x43C60: E28BB03C` advances the layer offset by 60 pointers; `0x43C64: E35B00F0` and `0x43C68` stop at 240 pointers. The record walk is layer, row, column over four layers.
- Every cell record has 22 `DatFile_Write` calls: one four-byte call at `0x43998`, 15 one-byte calls at `0x439B4`, `0x439D4`, `0x439F4`, `0x43A14`, `0x43A34`, `0x43A50`, `0x43A70`, `0x43A8C`, `0x43AA8`, `0x43AC8`, `0x43AE4`, `0x43B3C`, `0x43B5C`, `0x43B7C`, and `0x43B8C`, and six more four-byte calls at `0x43B08`, `0x43B2C`, `0x43BB0`, `0x43BD4`, `0x43BF8`, and `0x43C1C`. The one-byte sizes use raw word `E3A02001`; the four-byte sizes use `E3A02004`. Their sizes total `4 + 15 + 6*4 = 43` bytes.
- The pUnit ordinal is at byte offset 15: four face-damage bytes plus the first 11 one-byte fields (five flags, two flag bytes, one flag, two flag bytes, one flag). At `0x43AE8: E3A02004`, `MOV R2,#4` sets its size; `0x43AF8: 159033BC` loads `Soldier+0x3BC`; `0x43B08: EB016E69` writes that value. The preceding `Save_AssignRosterIndices @ 0x42EA0` stores each Soldier-array index at `Soldier+0x3BC` (`0x42EDC: E58313BC`).
- `Save_ReadMap @ 0x433D8` reads the same two dimension bytes at `0x43400` and `0x43418`, builds its row and column bounds with `10*dimY` and `10*dimX` (`0x43444: E200E0FF`, `0x43448: E3A0300A`, `0x4344C: E00B039E`; `0x43478: E201E0FF`, `0x4347C: E00B039E`), and uses the same 60-pointer row and four-layer walk (`0x43498..0x434B4`, `0x43880`, `0x438A8`, `0x438C8..0x438D4`).
- The reader consumes four bytes for pUnit at `0x436C0`, compares with the null value `0x7FFF` at `0x436CC`, loads `Map.apSoldiers[ordinal]` using `0x436D4: 10893100`, `0x436DC: 13822018`, and `0x436E0: 17933002`, then stores the pointer at cell `+0x30` at `0x436E8`. `0x436EC: 05845030` stores null for the sentinel.

## Original flagged-but-unplaced Soldier case

The executor found enemy Soldier pool slot 8 after load with HP 43, status 1, enemy-roster membership, and `pCell` pointing at cell `(0,0,0)` while that cell's `pUnit` is null. This is the original wire result when a tactical-roster Soldier has no cell pointer before save; the Soldier record and the MAP cell-owner record encode those two links separately.

- `Save_WriteSoldiers @ 0x42350` computes the record's `bInTact`. When the tactical flag is set, `0x423C0: E3A05001` starts R5 at 1. The enemy roster pointer is built at `0x42414: E3A03A15` / `0x42418: E3833F73` (Map+0x151CC), loaded at `0x4241C: E7913003`, and compared to the current Soldier at `0x42420: E1540003`. A match branches at `0x42424: 0A000024` to the store at `0x424C8: E7C45003`, which writes R5 to Soldier+0x40E. A listed enemy is therefore `bInTact=1` even if its `pCell` is null.
- The `stactflg` chunk preserves this flag. Its writer forms offset `0x40E` with `0x42DD0: E3A02B01` and `0x42DD8: E382200E`, then `0x42DDC: E7D33002` loads Soldier+0x40E; `0x42DE8: E3530000` tests it, `0x42DF0: 158D3004` stages 1 or `0x42DF4: 058DA004` stages 0, and `0x42DF8: EB0171AD` writes one byte. The reader finds that chunk at `0x416D0: EB0177B5`; `0x416E4: E3A06B01` and `0x416FC: E386600E` form Soldier+0x40E, `0x41728: EB0177DA` reads one byte, `0x41738: E3530001` compares with 1, and `0x41744: E7C30006` stores the result before reading Soldier bodies.
- The Soldier coordinate writer tests `bInTact` with `0x425D4: E21590FF` / `0x425D8: 0A000012`, then tests `Soldier+0x10` with `0x425DC: E5940010` / `0x425E0: E3500000` / `0x425E4: 0A00000F`. If the Soldier is flagged but `pCell==NULL`, that branch reaches `0x42628`. R10 was set to zero at `0x4238C: E3A0A000`; `0x42634: E58DA004` stores it in the three-byte coordinate buffer, which is written one byte at a time at `0x42638: EB01739D`, `0x42648: EB017399`, and `0x42658: EB017395`. Thus a tactical roster Soldier with a null pre-save cell gets coordinate bytes `0,0,0`.
- `Save_ReadSoldier` forms the same Soldier+0x40E offset with `0x41958: E3A06B01` and `0x4195C: E386600E`; `0x41960: E7D43006` loads the restored flag, `0x41964: E3530000` tests it, and `0x41968: 0A00001E` skips the coordinate arm only when clear. On flag 1 it reads x/y/z at `0x41988: EB017742`, `0x41998: EB01773E`, and `0x419A8: EB01773A`; zero bytes produce index zero through `0x419AC..0x419C8`. It loads the cell-table pointer from `Map+0x15338` at `0x419D8: E7933002` and stores it at Soldier+0x10 at `0x419DC: E5843010`. The original therefore restores this unplaced Soldier's `pCell` to `(0,0,0)`.
- The MAP owner field is separate. `0x43924: E3A0AC7F` and `0x43944: E38AA0FF` form the `0x7FFF` null-unit ordinal. The cell writer checks `MapCell+0x30` at `0x43AEC: E5940030` / `0x43AF4: E3500000`; for a null owner, `0x43B04: 058DA004` stages the sentinel and `0x43B08: EB016E69` writes it. The cell reader maps that sentinel back to null. It does not repair a Soldier's zero-coordinate placeholder into cell ownership.

The test snapshots null Soldier cells under their source `apSoldiers` slot before save. It verifies after `World_SaveSlot` that the raw writer's `Soldier+0x3BC` ordinal equals that slot, then keys the exception list by that canonical wire ordinal and only when the computed `bInTact` flag is 1 and the Soldier belongs to a tactical roster/reserve. It also reads the MAP origin record's ordinal from the actual chunk. After load, an ownerless origin pointer is accepted only for those exact wire ordinals, only when the MAP origin ordinal is `0x7FFF`, and only when the same `apSoldiers[ordinal]` has restored `bInTact=1` and points to the origin cell `(0,0,0)` whose `pUnit` is null. Any other flagged tactical Soldier without a resolved cell still fails; all previously placed Soldiers and all non-sentinel MAP owners still require reciprocal ownership. No cell owner is invented.

For a valid 6x5 MAP chunk, the record count is `4*50*60 = 12,000`, so its exact chunk size is `2 + 12,000*43 = 516,002` bytes. The unit ordinal is at record byte offset 15. Record index is `(layer*50 + row)*60 + column`.

## Test checks

The added test first checks the plane template and staged deploy references before the confirm input. The input hook calls the real `World_InvCloseAndCommit` path through `World_TactKeyDown/Up(PUFO_KEY_CONFIRM)`, then the test calls `TestWorldMapRefsFit(...,6,5)`. That scan requires every active 6x5 cell to exist, every Soldier cell reference, the deploy-cell pointer, and each cell owner to agree with the live grid, every owner to be in the live Soldier pool, and no owner or ground-item list in the omitted rows.

On a preflight failure only, the test prints the stage, actual dimensions/layers, tactical state and roster counts, the first pooled/placed Soldiers, the deploy cell, and the failing grid slot. Soldier output marks a null cell as `parked/no-cell`, a known cell with no owner as `grid-cell/no-owner`, and a reciprocal owner as `live-owned-cell`. It prints cell-owner and item-list pointer membership, marking `g_itemSlotEmpty` as a known sentinel and foreign pointers as invalid. Target-selection diagnostics report each XCOM candidate's pool/roster links, HP, status, cell/grid match, bounds, z>=1 condition, and positive ordinal condition. These messages do not change or bypass the preflight gates.

The target is selected from the existing XCOM roster only if it is alive, operative, on layer 1 or above, owns its cell, and has one positive index in `apSoldiers`. After the full deployed-reference preflight passes, the test records seed 3000 as the accepted spatial seed; it does not retry after a save or load failure. After `World_SaveSlot`, the test checks that `nSaveId` equals that source pool index. It reads the MAP chunk through `DatFile`, checks the two bytes and 516,002-byte size, and decodes the selected cell's four-byte ordinal at record offset 15. It restores the in-memory geometry to 6x6 before `World_LoadSlot`, then checks the loader takes dimensions 6x5 from the saved MAP chunk.

After load, it checks for 12,000 allocated cells across four layers, null cells outside the 6x5 bounds, and a living operative XCOM at its saved layer-1-or-higher cell. The identity is resolved from the captured source ordinal through the loaded `apSoldiers` array; the test does not use the reloaded `Soldier.nSaveId`.

The test prints seed 3000 as accepted only after the plane, pre-deploy, deployed-reference, and target spatial checks pass. It does not retry that seed after a save or load failure. This updated fixture has not been built or run in this task. The designated executor should report any spatial preflight failure as a concrete limit of this constructed mission; the test must not relax the owner checks or move units to make the crop fit.
