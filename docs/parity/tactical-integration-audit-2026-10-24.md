## Scope and method

This audit follows the Win64 app and world code from input through mission actions and return. I used decompilation to navigate, then checked the key call chains and memory owners against the live `pufobeta.exe.i64` ARM disassembly. The IDB stayed read-only.

The audit reads the current app, world, tactical action, combat, and test code. It does not claim that source wiring alone proves a playable full campaign. The focused Release build succeeds. The exact `build/tests/Release/test_geoscapeframe.exe` run ends with three name-input assertions, recorded in `.workers/luna-tactical/frame.log`; the tactical launch, movement, fire, reload, and throw checks now pass.

## Shutdown change

The shell's `World_FreeTactical` owns storage that cannot be passed to the full `Tact_Shutdown` free path: the RMP record and tactical context are inline, the look control is embedded, and world-owned blocks are shared with the app. The port extracts `Tact_ShutdownOutcome` for unit removal and mission result commit. Ported `Tact_Shutdown(0)` calls it to mirror the original's inline branch. `World_EndHookShutdown(0)` builds the live outcome environment and calls it before `World_FreeTactical`; the non-zero whole-list path stays separate.

Raw ARM proves that tactical side lists point into the global Soldier pool. In `Tact_SelectTeamUnits`, `0x397F0` loads offset `0x1198`; `0x397FC` reads the pool pointer, and `0x39880` stores that pointer in the XCOM side list based at `Map+0x15154`. In `Tact_SpawnAliens`, `0x3A714/0x3A71C` form offset `0x1194`; after `Soldier_CreateAndClassify` at `0x3A738`, the new count is loaded at `0x3A744`. The address `Map+0x1194+4*count` is the last pointer at `Map+0x1198+4*(count-1)`. `0x3A75C` loads it and `0x3A760` stores it in the enemy side list based at `Map+0x151CC`.

`Soldier_RemoveById @ 0x36B8C` loads the Map base at `0x36B90`, forms the global pool offset `0x1198` at `0x36B94/0x36BA8`, and overwrites its first argument with the Map base at `0x36BB4`. It frees and compacts that global array, then stores the lower count at `0x36C4C`. The `Tact_Shutdown` loops select records from side arrays at `Map+0x15244`, `Map+0x151CC`, and `Map+0x15154`; after each removal they reload the side count and advance the side index. They do not store a smaller side count.

The port now removes selected IDs from `apStrategCraftCopy` (the world roster) and leaves side-list counts for Map teardown. The app adapter clears cell and inventory links while records are live, passes a local `u16` count mirror, copies the new global count back, and zeroes the side counts before `World_FreeTactical` runs. That function sees zero counts on its second link-clear pass, then frees the map arrays; it does not free Soldier records. For ship removal and base demolition, the adapter copies their envs and points both Soldier-count fields at the same `u16` mirror; the local demolition env points to the local ship env. The world `i32` count is copied back once after outcome processing. `test_tactend.c` checks global survivors and unchanged side counts.

The old skip-one interpretation remains in `docs/parity/bugs.tsv:37`. Raw ARM disproves it: side counts are reloaded but never stored, and Soldier removal targets the global roster. I did not edit that invalid-encoding ledger file; this audit records the correction for an encoding-aware update.
